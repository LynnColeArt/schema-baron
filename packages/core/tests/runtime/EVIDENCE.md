# WP21 managed runtime and portable output evidence

Observed 2026-10-27 with Node 24.22.1/npm 11.19.1 on Linux, after `npm ci --ignore-scripts --offline`. No lifecycle script opt-in, dependency upgrade, hosted authentication or sync was performed.

## Behavior and authority

`runtime.start` accepts the current **output tree** revision and explicit `build` or `run` intent, with an optional loopback port. It invokes the selected Node executable and pinned local Next entry directly; it neither installs dependencies nor runs discovered npm scripts. The UI shows the approved working directory, executable, intended arguments, requested intent, actual port, model/draft/generated/running revision distinction, bounded job log and retry/stop/cancel actions. Actual pinned entry arguments are retained in the job. Opening a project only inspects status.

The current generated snapshot and output locator are recorded alongside WP20's metadata authority. A code-only promotion advances output tree revision even if the project revision is unchanged. The canonical plan ID preserves the revision on retry/recovery. Live Page compiles the **generated snapshot**, validates its declared key/filter/query context and resolves its selected route on the manager's ready port. Incomplete Record keys receive a Page-linked diagnostic and name the declared key inputs/new-record mode. Current drafts remain isolated static Preview content.

Every managed child starts in an owned detached process group. Approved cwd and Next entry are pinned with no-follow descriptors, and source/cwd/revision are rechecked after asynchronous port selection. Environment variables are allowlisted; author capability and ambient Node/npm options are not inherited. Line-buffered redaction covers configured secrets, bearer/credential patterns and scrypt hashes; persisted tail logs are capped at 32,768 characters. Jobs retain exit code/signal. Readiness requires the launched Next process's ready marker plus loopback HTTP, and stops on a deadline. TERM escalates to KILL, waits for the child close, and verifies no live process remains in the owned group; dead zombies waiting for the OS reaper are not running children. The initial process's exit also triggers descendant cleanup.

The real manager implements exported generator `RuntimeLifecyclePort.stopForPromotion`. Core invokes it before WP20's source rename; source authority and database schema/inode/locator validation run again after the callback. Stop refusal preserves active source. Existing row-only DB changes, old-tree backup, declared rebuildable `node_modules`/`.next`, unknown-file conflicts and modified-owned-file refusal remain intact.

## Portable export policy

`project.export` with a `.json` destination produces only a portable versioned definition, including rewritten database/output locators and removed `secretRef` references. Directory destinations through the same canonical async command copy the verified current source and definition, document `APPLICATION_DATABASE_PATH`, and include `deployment.env.example` placeholders. Both require approved paths; directory output must be unused. Definition creation is exclusive, and retries use canonical request IDs rather than overwriting existing files.

Data is absent by default, along with `.next`, dependencies, Studio metadata, managed identity stores, sessions and credentials. Explicit reviewed `includeData` uses a SQLite online backup and validates the snapshot schema and original source identity. Mapped identity data export is refused with an explanation: copying password hashes as ordinary data is unsafe, and deleting identity columns/rows would damage relationships. Export without data and provision an independent compatible identity source deliberately. No silent relational redaction or canonical DB mutation occurs.

The portable app defaults to `../data/application.sqlite` relative to `app/`, or explicit private deployment configuration. It can be moved and run independently after dependencies are installed. Managed runtime/process and guarded filesystem adapters are currently verified on Linux (`/proc` descriptor anchoring/process observation); Windows/macOS managed operation has not been verified. No detached hostile user-authored daemon sandbox is claimed; cleanup covers the generated process group, including its native query children. Broader mission functionality dependent on WP14/WP18 is not claimed here.

## Necessary shared integration rationale

- Model schemas add precise runtime state/command/route shapes and optional export output selection; both adapters discover those same schemas.
- Core registration connects the manager, cancellation, lifecycle and export to canonical command/idempotency/revision validation. Runtime failures carry Project/Page-linked diagnostics; asynchronous starts expose their job ID/202 response.
- Generation metadata retains the canonical generated snapshot/location for route/recovery authority without replacing WP20's per-plan tree revision counter or promotion rechecks.
- Registry permits an explicitly supplied synchronous definition-only handler alongside the async output export, preserving the established synchronous definition API.
- Storage accepts the validated portable definition projection and creates its file exclusively through an approved anchored parent; it cannot overwrite an unapproved existing definition.
- Studio's existing document-mode capability/workspace hooks show the actual runtime UI; the owner service routes generic job cancellation to the same owned manager and supplies transient capability redaction.
- The shared Record template's explicit context type closes the real supported-output build gap supplied by WP20. No compiler feature support or hook guard was weakened.
